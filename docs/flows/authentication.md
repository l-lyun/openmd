# 사용자 흐름: 이메일 기반 자체 인증

- 상태: 초안
- 관련 기능: [이메일 기반 자체 인증](../features/01-local-auth.md)
- 관련 계약: [인증 API](../contracts/api/authentication.md)

## 사용자 목표

본인 이메일로 계정을 만들고 안전하게 로그인 상태를 유지·갱신·종료한다.

## 시작 조건

- 가입: 사용자가 로그인 전 앱에서 회원가입을 선택한다.
- 로그인: 사용자가 로그인 전 앱을 열거나 보호된 화면에 접근한다.

## 완료 조건

- 가입: 이메일 소유, 비밀번호, 고유 닉네임과 필수 동의가 확인되고 자동 로그인된 상태로 홈에 도착한다.
- 로그인: 인증 상태가 만들어지고 원래 목적지 또는 홈에서 자신의 데이터에 접근한다.
- 로그아웃: 현재 로그인 유지 자격이 폐기되고 보호 화면과 개인 데이터가 보이지 않는다.

## 회원가입과 이메일 인증

1. 사용자가 1단계에서 이메일을 입력하고 인증 코드 발송을 요청한다.
2. 시스템은 이메일을 정규화하되 사용자 행은 만들지 않고, 혼동 문자를 제외한 대문자 영숫자 6자리 코드를 메일로 보낸다.
3. Redis에는 정규화 이메일의 keyed digest를 기준으로 코드 digest, 실패 횟수와 재발송 가능 시각을 TTL과 함께 저장한다.
4. 사용자는 같은 화면에서 인증 코드를 확인하고 비밀번호와 비밀번호 확인을 입력한다.
5. 클라이언트는 두 비밀번호의 일치를 확인하며, 서버에는 정책을 만족하는 비밀번호 하나만 전송한다.
6. 시스템은 인증 코드를 검증하고 UUID v4 `signUpToken`을 발급한다. 서버는 원문 대신 SHA-256 digest와 인증된 이메일 정보를 Redis에 15분간 저장하며, 이 시점에는 사용자 행이나 세션을 만들지 않는다.
7. 사용자는 2단계에서 닉네임을 입력하고 `중복 확인`을 명시적으로 실행한다.
8. 사용자는 MVP 임시 서비스 이용약관과 개인정보 수집·이용 동의 전문을 열람할 수 있으며 두 필수 항목에 동의한다.
9. 사용자가 가입 완료를 요청하면 서버는 가입 계속 자격, 닉네임 형식·전역 중복, 필수 약관 식별자·버전을 다시 검증한다.
10. 검증에 성공하면 NFC 정규화 닉네임과 필수 약관별 버전·동의 시각을 포함한 `ACTIVE` 사용자 행을 한 DB 트랜잭션에서 처음 생성하고 세션을 발급한다.
11. 클라이언트는 별도 로그인 화면 없이 홈으로 이동한다.

### 이미 인증을 요청한 이메일

1. 유효한 이메일 인증 상태가 있으면 재발송 제한에 따라 새 코드를 보낸다.
2. 새 코드를 발급할 때 Redis의 이전 코드 상태를 원자적으로 교체한다.
3. 이미 가입된 이메일인지와 관계없이 계정 존재 여부 노출 정책에 맞춘 동일한 접수 안내를 제공한다.

### 잘못되거나 만료된 코드

1. 코드가 일치하지 않으면 Redis 원자 연산으로 실패 횟수를 올린다.
2. 5회 실패하면 해당 코드를 즉시 무효화한다.
3. TTL이 지났거나 실패 횟수가 소진된 코드는 계정을 활성화하지 않는다.
4. 사용자는 60초 재발송 간격 이후 새 코드를 요청할 수 있다.

## 로그인과 인증 상태 갱신

1. 사용자가 이메일과 비밀번호를 입력한다.
2. 시스템은 동일한 규칙으로 이메일을 정규화하고 자격 증명을 확인한다.
3. 인증 실패, 미인증, 정지·탈퇴 상태에는 계정 세부 상태를 과도하게 노출하지 않는 실패 응답을 제공한다.
4. 인증에 성공하면 Access Token과 서버 형식 `<randomSessionId>.<256-bit random secret>`의 Refresh Token을 발급한다. 클라이언트는 전체 값을 opaque하게 취급한다.
5. 사용자는 원래 목적지 또는 홈으로 이동하고 해당 사용자의 학습 상태를 불러온다.
6. 서버는 token에서 충분히 랜덤한 session ID를 파싱해 Redis 세션을 조회하되 이를 인증 근거로 신뢰하지 않고, secret의 SHA-256 digest가 현재 값과 일치할 때만 인정한다. 원문은 DB와 Redis에 저장하지 않는다.
7. Access Token이 만료되면 클라이언트는 Refresh Token으로 갱신을 요청한다.
8. Redis Lua 또는 동등한 원자 연산이 현재 digest를 확인하고, 기존 digest tombstone 생성과 새 digest 교체를 한 번에 수행한다.
9. 갱신에 성공하면 이전 Refresh Token은 다시 사용할 수 없고 새 Access/Refresh Token을 받는다.
10. 갱신도 실패하면 현재 작업을 가능한 범위에서 보존하고 로그인 화면으로 안내한다.

### 갱신 자격 재사용 감지

1. 이미 회전된 Refresh Token digest가 TTL tombstone에서 발견되면 재사용으로 판정한다.
2. 해당 클라이언트는 인증 정보를 제거하고 다시 로그인한다.
3. Redis에서 해당 session/family를 원자적으로 폐기한다.

## 로그아웃

1. 사용자가 프로필의 설정에서 로그아웃을 선택한다.
2. 시스템은 Redis의 현재 session/family를 폐기한다. 이미 만료됐더라도 로그아웃 결과는 동일하게 처리한다.
3. 클라이언트는 Access/Refresh Token과 화면의 개인 학습정보를 제거한다.
4. 로그인 화면으로 이동하며 뒤로가기로 보호 화면에 다시 진입할 수 없다.

## 중단과 재개

- 메일 발송 실패는 `AUTH_008`로 반환하고, 서버는 발송하려던 digest가 여전히 현재 값일 때만 Redis 상태를 원자 삭제해 재발송 cooldown을 해제한다. 이미 새 코드로 교체됐다면 그 상태는 보존한다.
- 이메일 인증 대기는 앱을 닫아도 코드 TTL 동안 Redis에 남지만 사용자 행을 만들지 않는다. 다시 가입을 시작하면 재발송 제한에 따라 같은 이메일의 인증 상태를 교체한다.
- `signUpToken`은 발급한 클라이언트의 메모리에서만 보관하며 15분 후 만료된다. 새로고침·앱 종료·다른 기기 전환으로 원문을 잃거나 만료되면 이메일 인증부터 다시 시작한다.
- 향후 소셜 신규가입은 제공자 인증 성공 후 2단계로 진입한다. 닉네임·약관을 마치지 않고 이탈한 사용자의 장기 상태와 재진입 경로는 소셜 로그인 백엔드 작업에서 별도 확정한다.
- 코드를 다른 기기에서 제출하면 그 기기가 `signUpToken`을 받는다. 사용자 행은 만들어지지 않으며 다른 기기에서 가입 계속 자격을 복구하지 않는다.
- 최종 가입 응답이 유실되면 브라우저는 Cookie가 도착했을 가능성을 확인하기 위해 refresh를 한 번 호출한다. 성공하면 홈으로 이동하고, 자격 없음이면 가입 완료를 반복하지 않고 로그인한다. 네이티브는 응답 body를 잃으면 로그인으로 복구한다.
- 세션 만료 중 작성 중인 입력은 민감도와 데이터 정합성이 허용하는 범위에서 로컬에 임시 보존한다.

## 열린 질문

- 법률 검토 후 사용할 실제 약관 식별자·버전과 전문
- 접근 자격 만료 중 작성 중인 붙여넣기나 답안의 보존 범위
- 현재 기기 로그아웃 외에 모든 기기 로그아웃을 초기 제공할지
